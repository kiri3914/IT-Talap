## 1. Цели проекта

### 1.1 Основная цель (для автора)

Закрепить и расширить навыки дата-инженерии на реальной сквозной задаче: от сбора сырых данных из внешних источников до публичного аналитического продукта.

Целевые компетенции, которые проект должен развить:

| Компетенция | Где отрабатывается |
|---|---|
| Ingestion из разнородных источников | Фаза 1–2 |
| Объектное хранилище как raw-слой | Фаза 1 |
| Историзация данных (SCD Type 2) | Фаза 2 |
| Дедупликация и entity resolution | Фаза 2 |
| dbt: модели, тесты, документация, lineage | Фаза 2 |
| Колоночная аналитическая СУБД (ClickHouse) | Фаза 2 |
| Data Quality как отдельный слой | Фаза 2 |
| Оркестрация нетривиальных пайплайнов | Все фазы |
| LLM для structured extraction | Фаза 2 |
| BI и публикация результатов | Фаза 3 |

### 1.2 Продуктовая цель

Дать соискателям и работодателям региона объективную картину рынка IT-труда: реальные зарплатные вилки, динамику спроса по направлениям, скорость закрытия вакансий, устаревающие и растущие технологии.

### 1.3 Ключевое отличие от существующих решений

Проект **не является агрегатором вакансий**. Агрегаторов достаточно. Уникальная ценность — **накопленная история состояний рынка**, которой не хранит ни одна площадка. Из ежедневных снимков рождаются метрики, недоступные при взгляде на текущий срез: время жизни вакансии, частота перепубликаций, изменение зарплатных предложений во времени, сезонность найма.

Из этого следует главный операционный вывод: **накопление истории начинается с первого дня и не может быть наверстано позже**. Приоритет Фазы 1 — запустить ежедневный сбор, даже если обработка данных ещё не готова.

## 2. Границы проекта

### 2.1 В скоупе

- Сбор вакансий IT-направления по Казахстану, Кыргызстану, Узбекистану; Россия — как база для сравнения
- Ежедневная фиксация состояния каждой вакансии
- Нормализация профессий, грейдов, скиллов, зарплат
- Дедупликация вакансий между площадками
- Аналитические витрины и публичный дашборд
- Регистрация пользователей и подписки на фильтры (Фаза 4)

### 2.2 Вне скоупа

- Отклик на вакансию через платформу
- Хранение и обработка персональных данных резюме сверх минимально необходимого
- Скрейпинг площадок, прямо запрещающих его в ToS
- «ИИ-подбор вакансий по резюме» как отдельный продукт — на текущем этапе избыточен

### 2.3 Явные ограничения источников

| Желаемая метрика | Доступность | Решение |
|---|---|---|
| Количество откликов | Недоступна публично ни на одной площадке | Заменяется на время жизни вакансии |
| Динамика откликов во времени | Недоступна | Заменяется на факт перепубликации |
| Факт закрытия вакансии | Недоступен явно | Выводится из исчезновения из выдачи |
| Реальная зарплата нанятого | Недоступна | Работаем только с заявленной вилкой |

Формулировка «за какое время закрылась вакансия» в дальнейшем понимается как **время присутствия вакансии в выдаче**, что не тождественно факту найма.

### 3.2 Требования к сбору

- Перед подключением каждого источника — проверка `robots.txt` и пользовательского соглашения; результат проверки фиксируется в `docs/sources/<source>.md`
- Соблюдение rate limits. Для hh API — не более 2000 запросов в час с IP, обязательный экспоненциальный backoff при `429`
- Осмысленный `User-Agent` с контактом
- Идемпотентность: повторный запуск загрузки за ту же дату не должен порождать дублей
- Полное сохранение сырого ответа без предварительной обработки

### 4.2 Обоснование выбора технологий

| Технология | Роль | Обоснование |
|---|---|---|
| Python 3.12 + httpx + Pydantic | Ingestion | Валидация схемы источника на входе. Pydantic ловит изменения API раньше, чем они попортят данные |
| MinIO (локально) / S3 | Raw-слой | Дешёвое неизменяемое хранилище. Позволяет пересчитать всю историю при изменении логики нормализации |
| PostgreSQL 16 | Staging + Core | Транзакционность, зрелые оконные функции, знакомый инструмент |
| ClickHouse | Marts | Профиль нагрузки — агрегации по датам и категориям. Дефицитный навык на рынке |
| dbt-core | Трансформации | Версионирование логики, тесты, автодокументация, lineage. Центральный обучающий элемент проекта |
| Airflow 2.9 | Оркестрация | TaskFlow API, dynamic task mapping по источникам |
| Superset | BI | Открытый, self-hosted, интеграция с ClickHouse из коробки |
| Docker Compose | Окружение | Воспроизводимость с первого дня |

### 4.3 Технологии, сознательно исключённые

| Технология | Причина исключения |
|---|---|
| Apache Spark | Объём данных на два-три порядка ниже порога окупаемости. Оверхед запуска джобы превышает время обработки |
| Hadoop / HDFS | Устаревший слой, вытесненный объектными хранилищами |
| Kafka | Нет источника реального времени в Фазах 1–3. Возможен пересмотр в Фазе 5 |
| Debezium / CDC | Нет собственной транзакционной базы с изменяемыми данными до Фазы 4 |

Решения зафиксированы как ADR в `docs/adr/`. Пересмотр допустим при изменении входных условий, а не по желанию попробовать инструмент.

### 4.4 Опциональное расширение

Если требуется отработать концепции lakehouse без кластера — **DuckDB + Apache Iceberg** поверх MinIO. Даёт table format с версионированием и time travel, концептуально эквивалентно Spark + Iceberg, но исполняется на одной машине.

## 6. Ключевые алгоритмы

### 6.1 Дедупликация вакансий

Самая сложная задача проекта. Одна позиция может публиковаться на трёх площадках с разными формулировками, а также перепубликовываться той же компанией.

**Этап 1 — точное совпадение.**
`hash(normalize(title) + company_sk + city)`. Нормализация: нижний регистр, удаление пунктуации и эмодзи, приведение синонимов («разработчик» → «developer»).

**Этап 2 — нечёткое совпадение.**
Для не сматченных на этапе 1 — сравнение описаний. Косинусное сходство эмбеддингов, порог 0.92. Кандидаты ограничиваются одной компанией и окном ±14 дней.

**Этап 3 — ручное разрешение.**
Пары со сходством в диапазоне 0.85–0.92 попадают в очередь ручной проверки. Решения сохраняются и используются как обучающая выборка для калибровки порога.

**Метрика качества:** на размеченной вручную выборке из 500 пар — precision ≥ 0.95, recall ≥ 0.85. Precision приоритетнее: ложное склеивание двух разных вакансий искажает статистику сильнее, чем пропущенный дубль.

### 6.2 Нормализация зарплат

1. Определить валюту. При отсутствии — вывести из страны размещения
2. Определить gross/net. Ключевые слова в тексте, при неоднозначности — `NULL`, запись исключается из зарплатной статистики
3. Привести к USD по курсу на `published_at`, не на дату расчёта
4. Сохранить оригинальные значения без изменений
5. Отбросить выбросы: значения вне интервала [p1, p99] по профессии помечаются флагом и исключаются из агрегатов

**Обработка «вилок»:** при наличии обеих границ для медианной статистики используется среднее арифметическое границ. Односторонние вилки («от X») учитываются отдельно и не смешиваются с двусторонними.

### 6.3 Извлечение атрибутов из текста (LLM)

Применяется к описанию вакансии для получения структурированного JSON.

**Извлекаемые поля:** список скиллов с флагом обязательности, грейд, формат работы, наличие релокации, язык требований, годы опыта.

**Требования:**
- Модель уровня Claude Haiku, structured output, температура 0
- Обработка батчами, ежедневный лимит расходов
- Кэширование по хешу описания: повторно один текст не обрабатывается
- Результат сохраняется в отдельную таблицу с версией промпта — при изменении промпта возможен пересчёт
- Регулярные выражения выполняются **до** LLM; модель обрабатывает только то, что не покрыто правилами

**Валидация:** ручная разметка 200 вакансий, целевая точность извлечения скиллов ≥ 0.90.

## 7. Оркестрация

### 7.1 DAG `ingest_daily`

Расписание: ежедневно в 03:00 UTC+6.

```
start
  ├─ [dynamic task mapping по источникам]
  │    fetch_source(source) → validate_schema → write_raw_to_s3
  ├─ fetch_currency_rates
  └─ check_ingestion_completeness
       └─ trigger dbt_transform
```

Отказ одного источника не блокирует остальные. Порог алерта: падение любого источника или отклонение объёма загрузки более чем на 40% от скользящего среднего за 7 дней.

### 7.2 DAG `dbt_transform`

```
dbt run --select staging
  └─ dbt test --select staging
       └─ dbt run --select core
            └─ dbt test --select core
                 └─ dbt run --select marts
                      └─ dbt test --select marts
                           └─ export_to_clickhouse
```

Провал тестов останавливает конвейер. Витрины сохраняют предыдущее валидное состояние.

### 7.3 DAG `detect_closures`

Ежедневно после `ingest_daily`. Помечает вакансии, отсутствующие в свежей выдаче, проставляет `closed_at` и рассчитывает `lifetime_days`.

**Защита от ложных закрытий:** вакансия помечается закрытой только после отсутствия в **двух последовательных** выгрузках. Один сбой парсера не должен «закрыть» весь рынок.

## 8. Качество данных

### 8.1 Обязательные проверки

| Слой | Проверка |
|---|---|
| Raw | Файл за дату существует, размер больше нуля |
| Raw | Количество записей отклоняется не более чем на 40% от среднего за 7 дней |
| Staging | `source_id` уникален в пределах источника и даты |
| Staging | `published_at` не в будущем и не старше 2 лет |
| Staging | `salary_from` ≤ `salary_to` |
| Core | Ровно одна текущая версия на `vacancy_nk` (`is_current = true`) |
| Core | Отсутствие разрывов и пересечений интервалов `valid_from`/`valid_to` |
| Core | Все FK разрешаются |
| Marts | Медианная зарплата по профессии не меняется более чем на 30% за день |
| Marts | Доля вакансий с нераспознанной профессией ниже 15% |

### 8.2 Журнал загрузок

Обязательная таблица `meta.ingestion_log`: `run_id`, `source`, `started_at`, `finished_at`, `status`, `records_fetched`, `records_written`, `error_message`.

Без этого журнала через три месяца невозможно объяснить провалы в данных.

## 9. Дорожная карта

### Фаза 1 — Накопление истории (2–3 недели)

**Задача:** любой ценой начать ежедневный сбор.

- Docker Compose: Postgres, MinIO, Airflow
- Клиент hh API для kz и uz
- DAG `ingest_daily`, запись сырья в MinIO
- Минимальная staging-модель, чтобы видеть данные
- `meta.ingestion_log`

**Критерий готовности:** 14 дней подряд без пропусков собираются данные, сырьё лежит в S3.

### Фаза 2 — Обработка (4–6 недель)

- Подключение Telegram и Хабр Карьеры
- dbt: staging → core → marts
- SCD2 по вакансиям, `fct_vacancy_snapshot`
- Дедупликация, этапы 1 и 2
- Справочники профессий и скиллов, нормализация зарплат
- LLM-извлечение атрибутов
- ClickHouse, тесты качества данных

**Критерий готовности:** витрины считаются, тесты зелёные, доля нераспознанных профессий ниже 15%.

### Фаза 3 — Публикация (2–3 недели)

- Superset, набор дашбордов
- Публичный доступ, домен, базовая SEO-оптимизация
- Методологическая страница: как считается, чего не показывает

**Критерий готовности:** посторонний человек открывает дашборд и получает ответ на вопрос «сколько платят Python-разработчику middle в Алматы».

### Фаза 4 — Пользователи (3–4 недели)

- Django-приложение: регистрация, сохранённые фильтры
- Email-подписка на новые вакансии по фильтру
- Персональная страница «мой рынок»: динамика по интересующим направлениям

Подписка на фильтр реализуется до любых форм «умного подбора»: она проще, надёжнее и полезнее.

### Фаза 5 — Развитие

- Ежеквартальные аналитические отчёты о рынке
- Публичное API
- Прогнозирование спроса по направлениям
- Мониторинг Telegram в реальном времени — здесь Kafka становится оправданной

## 10. Правовые и этические требования

- Собираются только публично опубликованные данные вакансий
- Персональные данные соискателей не собираются
- Контактные данные из текстов вакансий (телефоны, личные email) не сохраняются и вырезаются на этапе staging
- Соблюдаются rate limits и `robots.txt` каждого источника
- Публикуются агрегаты; полные тексты чужих вакансий не воспроизводятся, даётся ссылка на первоисточник
- На дашборде указывается источник данных и дата последнего обновления
- Методология расчёта публикуется открыто

## 11. Риски

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Изменение схемы API источника | Высокая | Среднее | Валидация Pydantic на входе, алерт при несоответствии |
| Блокировка при парсинге HTML | Средняя | Среднее | Приоритет официальным API, backoff, ротация UA |
| Низкое качество дедупликации | Высокая | Высокое | Ручная разметка, приоритет precision, очередь разрешения |
| Малый объём данных по KZ для статистики | Средняя | Среднее | Порог в 5 наблюдений, укрупнение группировок |
| Разрастание стека и потеря темпа | **Высокая** | **Высокое** | ADR на каждый новый инструмент; запрет на добавление технологий вне дорожной карты |
| Потеря истории из-за простоя пайплайна | Средняя | **Критическое** | Алерты на пропуск загрузки, ручной backfill в течение 24 часов |

Главный риск проекта — не технический. Пет-проекты чаще умирают от переусложнения стека, чем от скучных инструментов.
