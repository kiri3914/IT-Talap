# Находка №3: сверка с сайтом вскрыла четыре проблемы

**Дата:** 2026-09-14
**Метод:** сверили одну вакансию на hh.ru с тем, что лежит у нас
(136979155, Senior Database Engineer, EXNESS)

Урок метода: в агрегатах эти проблемы невидимы. Их находит только
ручная сверка одной записи — то, что стоит делать регулярно.

---

## 1. `salary_range.mode` — зарплата не всегда за месяц

**Самое важное.** У вакансии два поля зарплаты, и они НЕ дубликаты:

```json
"salary":       {"from": 7000, "to": null, "gross": false, "currency": "EUR"}
"salary_range": {"from": 7000, "to": null, "gross": false, "currency": "EUR",
                 "mode": {"id": "MONTH", "name": "За месяц"},
                 "frequency": null}
```

**`salary_range.mode` говорит, за какой период указана сумма.** Если где-то
стоит `HOUR`, `DAY` или `PROJECT`, то 7000 — это не месячная зарплата,
и сравнивать её с месячными нельзя.

Ставка 5 000 ₸/час и оклад 5 000 ₸/месяц в нашей медиане сейчас одно и то же.

**Проверить немедленно:**

```sql
select payload -> 'salary_range' -> 'mode' ->> 'id' as режим,
       payload -> 'salary' ->> 'currency'           as валюта,
       count(*)
from raw_landing.hh_vacancies
where kind = 'details' and payload -> 'salary_range' is not null
group by 1, 2 order by 3 desc;
```

Если всё `MONTH` — повезло, но фильтр всё равно нужен: он защитит,
когда появится первая почасовая вакансия.

Если есть другие значения — **все посчитанные медианы недействительны**
до добавления фильтра `mode = 'MONTH'`.

### Заодно опровергнут прежний вывод

В `findings-01` записано: «`salary_range` не используется вообще, ноль
вакансий, где заполнено только оно». Это верно, но вывод «полагаемся
на `salary`» — неверен. Поля дублируют суммы, но `salary_range` несёт
**дополнительную информацию**, которой нет в `salary`.

## 2. `work_format` есть в данных — выводить не нужно

```json
"work_format":          [{"id": "HYBRID", "name": "Гибрид"}]
"work_schedule_by_days": [{"id": "FIVE_ON_TWO_OFF", "name": "5/2"}]
"working_hours":         [{"id": "HOURS_8", "name": "8 часов"}]
"employment_form":       {"id": "FULL", "name": "Полная"}
```

В ТЗ §5.2 поле `work_format` (office / hybrid / remote) предполагалось
выводить из текста. Оказалось, hh отдаёт его структурно — вместе с графиком
и длиной смены, которых в ТЗ вообще не было.

Это готовый разрез «сколько платят на удалёнке против офиса», и он
не требует ни правил, ни LLM.

---

## 3. Роль проставлена неверно самим работодателем

```
"name": "Senior Database Engineer"
"professional_roles": [{"id": "165", "name": "Дата-сайентист"}]
```

Database Engineer отнесён к дата-сайентистам. Ошибка на стороне
работодателя, и таких наверняка много: роль выбирают из списка наспех.

**Следствие:** `mart_salary_stats` в разрезе профессий наследует чужие
ошибки классификации. Медиана дата-сайентистов завышается за счёт
инженеров, и наоборот.

Это довод в пользу собственного справочника профессий с распознаванием
по заголовку — не вместо `professional_role`, а как проверка.

**Оценить масштаб:** взять вакансии, где заголовок явно противоречит роли
(«developer» в роли «Дизайнер» и т.п.), посчитать долю.

## 4. `key_skills` пустой чаще, чем казалось

У этой вакансии `key_skills: []`, хотя в описании перечислены PostgreSQL,
MongoDB, ClickHouse, Cassandra, Prometheus, Grafana.

Замер в `findings-01` дал 63.7% заполненности — но считались только
непустые. Реальная картина для `mart_skill_popularity` хуже: технологии
есть в тексте, но не в поле.

Извлечение скиллов из описания — отдельная задача, и вот тут LLM
действительно окупается, в отличие от телеграма.

## Что ещё нашлось полезного

| Поле | Зачем |
|---|---|
| `billing_type` | `free` против платного размещения — косвенный признак серьёзности вакансии |
| `internship`, `night_shifts` | фильтры, которых не было в ТЗ |
| `languages` | требования к языкам структурно |
| `initial_created_at` | отличается от `published_at` при перепубликации — **готовый признак для метрики перепубликаций** |
| `address.lat/lng` | координаты; здесь 34.68, 33.04 — Кипр, а `area` = Астана |

`initial_created_at` стоит проверить отдельно: если он действительно
сохраняется при перепубликации, метрика «частота перепубликаций»
из ТЗ §3 считается напрямую, без эвристик.

## Релокация: `area` ≠ место работы

```
"area":    {"id": "159", "name": "Астана"}
"address": {"city": "Лимасол", "lat": 34.687, "lng": 33.036}
```

Вакансия опубликована в разделе Астаны, работа на Кипре, зарплата €7000 —
примерно впятеро выше медианы Астаны. Одна такая в группе из пяти
наблюдений делает медиану бессмысленной.

**Проверить масштаб:**

```sql
select payload -> 'area' ->> 'name'    as город_публикации,
       payload -> 'address' ->> 'city' as город_работы,
       payload -> 'salary' ->> 'currency' as валюта,
       count(*)
from raw_landing.hh_vacancies
where kind = 'details'
  and payload -> 'address' ->> 'city' is not null
  and payload -> 'address' ->> 'city' <> (payload -> 'area' ->> 'name')
group by 1, 2, 3 order by 4 desc limit 30;
```

**Варианты решения:**

1. Считать город по `address.city`, если он есть, иначе по `area.name`.
   Честнее: человек работает там, где работа.
2. Отдельный флаг `is_relocation` и исключение из городских медиан.
3. Косвенный признак: валюта EUR или USD у вакансии «в Астане» почти
   наверняка означает зарубежного работодателя.
