## 2. Способ доступа — проверено

Один API `api.hh.ru` на все страны. hh.kz / hh.uz / hh.kg — не отдельные API,
различаются параметрами `area` и `host`. Подтверждено.

### Открыто без авторизации

| Эндпоинт | Статус |
|---|---|
| `GET /areas` | 200 ✅ |
| `GET /professional_roles` | 200 ✅ |

### Требует авторизации И корректного User-Agent

| Эндпоинт | Без токена | С токеном, плохой UA | С токеном и UA |
|---|---|---|---|
| `GET /vacancies` | 403 forbidden | 400 bad_user_agent | **200 ✅** |

**Токен.** `POST /token` с `grant_type=client_credentials`, client_id и client_secret
приложения с dev.hh.ru. Живёт 14 дней. Redirect URI не нужен — он только
для authorization_code, когда действуют от имени пользователя.

**User-Agent — отдельная ловушка.** hh отвечает:

```json
{"description":"Bad User-Agent header",
 "errors":[{"value":"blacklisted","type":"bad_user_agent"}]}
```

Причём на ЛЮБОЙ запрос к /vacancies, независимо от параметров — проверено
перебором 11 комбинаций area/role/host/order_by/page/date_from.

Виновником оказался **`example.com` в контакте** (остался placeholder из шаблона).
Проверено 2026-09-11 перебором 8 форматов:

| User-Agent | Код |
|---|---|
| `Talap/0.1 (talap-project; contact@example.com)` | **400** |
| `Talap/1.0 (kiri.bekos@gmail.com)` | 200 |
| `Talap (kiri.bekos@gmail.com)` | 200 |
| `Talap` | 200 |
| `talap-app/1.0 (kiri.bekos@gmail.com)` | 200 |

Вывод: формат заголовка свободный, но **домен example.com в чёрном списке**.
Имя приложения совпадать с зарегистрированным на dev.hh.ru не обязано.

Проверено 2026-09-04 с тремя вариантами заголовков:

```
[осмысленный UA]  403 {"errors":[{"type":"forbidden"}]}
[браузерный UA]   403 {"errors":[{"type":"forbidden"}]}
[без UA]          403 {"errors":[{"type":"forbidden"}]}
```

**Вывод: дело не в User-Agent.** Анонимный доступ к поиску вакансий закрыт.
Требуется регистрация приложения и токен.

Регистрация: https://dev.hh.ru/admin — создать приложение, получить credentials.

## 3.1. Параметр `host` — не использовать

`host=hh.kg` отвергается:

```json
{"description":"Invalid host argument","bad_argument":"host",
 "errors":[{"value":"host","type":"bad_argument"}]}
```

При этом `host=hh.kz` и `host=hh.uz` принимаются — ошибка вылезла только
на Кыргызстане. География полностью задаётся `area`, поэтому параметр убран
из запросов совсем: он влиял бы только на домен в ссылках ответа.

Урок: значения, допустимые для одной страны, могут быть недопустимы для другой.
Проверять надо каждую, а не экстраполировать с первой успешной.

## 4. Ограничения — частично проверено

### Измерено 2026-09-11, первый боевой сбор

| Страна | area | IT-вакансий | Запросов | Время |
|---|---|---|---|---|
| Казахстан | 40 | **2 027** | 2 064 | 455 с |
| Узбекистан | 97 | **1 113** | 1 143 | 248 с |
| Кыргызстан | 48 | — | — | падал на `host` |

Всего вакансий по Казахстану (без фильтра роли) — 36 622, то есть
**IT составляет около 5.5% рынка**.

Объём сырья: KZ ~11.7 МБ, UZ ~5.3 МБ в gzip за день (списки + детали).
В год при таком темпе — единицы гигабайт.

**Глубина выдачи ни разу не превышена:** ни один срез `area × professional_role`
не дал больше 2000, нарезка по окнам дат не сработала ни разу.
Значит, ветка `_split_by_date` на боевых данных не исполнялась.

Проверять её надо на России — объёмы там на порядок больше:

```bash
.venv/bin/python scripts/check_depth_limit.py --country ru
.venv/bin/python scripts/check_depth_limit.py --country ru --collect
```

Скрипт находит роль с наибольшим `found`, бинарным поиском измеряет,
с какой страницы API перестаёт отдавать данные, и сравнивает с константой
`DEPTH_LIMIT = 2000`. С `--collect` прогоняет полный сбор и показывает,
сколько раз делилось окно и не потерялось ли что-то.

Россия добавлена в `COUNTRIES`, но **не входит в ежедневный сбор**:
в `DEFAULT_COUNTRIES` только kz, uz, kg.

**Скорость деталей:** ~4.5 запроса в секунду. Первый день грузит всё,
со второго — только дельту (новые ID), то есть десятки вакансий вместо тысяч.

- [ ] Реальная граница глубины выдачи (`page * per_page`; в документации 2000)
- [ ] Rate limit: заявленный и наблюдаемый
- [ ] `found` по каждой из 25 IT-ролей на страну — сколько срезов упирается в лимит
- [ ] Есть ли полное описание в списке или только в `/vacancies/{id}`
- [ ] Работают ли `date_from` / `date_to` для нарезки окон
- [ ] Отдаёт ли API признак архивной/закрытой вакансии

Текущий код исходит из документированного лимита 2000 — константа `DEPTH_LIMIT`
в `ingestion/sources/hh.py`. Поправить по факту замера.
