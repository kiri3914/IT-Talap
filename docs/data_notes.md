# Наблюдения по сырым данным hh

Из просмотра реальных вакансий, 2026-09-11. Влияет на staging-модель и ТЗ.

---

## 1. `employer.id` — стабильный ключ компании. Это меняет план

```json
"employer": {"id": "9777596", "name": "Азия Ритейл", "url": "..."}
```

В ТЗ §5.2 `dim_company` строилась на нормализации названия: «Kaspi.kz» / «ТОО Kaspi» /
«Kaspi Bank» — три написания одной компании. Внутри hh эта проблема **не стоит**:
у работодателя есть стабильный числовой id.

**Следствие:** нормализация имён нужна только для склейки компаний МЕЖДУ источниками
(hh × rabota.kz × телеграм). Внутри hh — просто `employer.id`.
Задача из Фазы 2 сильно упрощается и сдвигается на момент подключения второго источника.

---

## 2. Два поля зарплаты, оба могут быть null

```json
"salary": null,
"salary_range": null
```

`salary_range` — более новое поле, `salary` — историческое. Нужно читать оба
и брать непустое. Если в staging смотреть только на `salary`, часть вилок потеряется.

**Проверить:** посчитать долю вакансий, где заполнено только одно из двух.

---

## 3. Грейда в данных НЕТ

Есть только опыт:

```json
"experience": {"id": "between3And6", "name": "От 3 до 6 лет"}
```

Значения: `noExperience`, `between1And3`, `between3And6`, `moreThan6`.

Это **не грейд**. Middle с 4 годами и Senior с 4 годами попадут в одну корзину.
Поле `grade` из ТЗ §5.2 придётся выводить из заголовка и описания —
сначала правилами (`junior|младший|стажёр` и т.п.), потом LLM для остатка.

**`experience` при этом полезен** как самостоятельный разрез и как признак
для распознавания грейда.

---

## 4. `key_skills` структурированы, но без признака обязательности

```json
"key_skills": [{"name": "MS SQL Server"}, {"name": "1С: Бухгалтерия"}, ...]
```

Хорошая новость: скиллы отдельным полем, парсить текст не нужно.
Плохая: `bridge_vacancy_skill.is_required` из ТЗ §5.2 **заполнить нечем** —
hh не различает требование и пожелание.

**Решение:** либо убрать `is_required` из модели, либо извлекать из описания
(«будет плюсом», «желательно») — но это уже LLM, и на старте не нужно.

Ещё видно, что справочник скиллов грязный: рядом с `SQL` и `MS SQL Server`
лежит `Аналитическое мышление` — это не технология. Справочник `dim_skill`
придётся чистить и категоризировать вручную.

---

## 5. Есть флаг `archived` — влияет на детекцию закрытий

```json
"archived": false,
"type": {"id": "open", "name": "Открытая"}
```

В ТЗ §2.3 записано, что факт закрытия недоступен и выводится из исчезновения
из выдачи. Частично это не так: у hh есть явный признак архива.

**Проверить:** остаётся ли вакансия доступной по `/vacancies/{id}` после снятия
и меняется ли `archived` на `true`. Если да — детекция закрытий станет точнее
правила двух пропусков: можно будет отличить «сняли» от «наш парсер моргнул».

Это стоит выяснить на реальных данных через неделю, когда часть сегодняшних
вакансий закроется.

---

## 6. Контакты: поле есть, значит его надо резать

```json
"show_contacts": false,
"contacts": null
```

Здесь `null`, но поле существует — значит, где-то оно заполнено.
Требование ТЗ §10 (не хранить контакты) относится именно к нему,
плюс к телефонам и почте внутри `description`.

Резать на staging, в raw оставлять как есть.

---

## 7. Описание — HTML

`description` приходит размеченным (`<p>`, `<ul>`, `<strong>`).
На staging нужно снимать теги: для поиска, для LLM-извлечения и для эмбеддингов
дедупликации. Сырой HTML сохраняем в raw без изменений.

---

## 8. Город есть в двух местах

```json
"area": {"id": "2760", "name": "Бишкек"},
"address": {"city": "Бишкек", "lat": 42.88, "lng": 74.59, ...}
```

`area.id` — стабильный справочный ключ, его и брать. `address` заполнен не всегда,
но даёт координаты — пригодится, если дойдём до карты.

`specializations: []` — пустой, поле устаревшее, игнорируем.

---

## Что проверить на всём массиве

Первые запросы к данным, до всякой staging-модели:

- [ ] доля вакансий с заполненной зарплатой (`salary` или `salary_range`)
- [ ] доля, где заполнено только `salary_range`
- [ ] распределение по `experience`
- [ ] сколько вакансий имеют непустые `key_skills`
- [ ] сколько уникальных `employer.id` и какая доля вакансий у топ-10
- [ ] доля вакансий, где `archived = true`
- [ ] распределение валют (KZT / UZS / KGS / USD / RUB)

Эти семь цифр определят, что вообще можно посчитать, и стоит получить их
до написания первой dbt-модели.
