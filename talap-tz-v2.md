## 0. Что изменилось относительно v1.0

Девять правок, внесённых по итогам ревью. Каждая — с причиной, чтобы через полгода было понятно, почему так.

| # | Правка | Причина |
|---|---|---|
| 1 | Порядок ingestion: `fetch → write_raw → validate → alert` вместо `fetch → validate → write` | Валидация до записи превращает страховку от изменения схемы в механизм потери данных. Raw-слой принимает всё. |
| 2 | Raw-слой — удалённый бакет (R2/B2), не MinIO на том же VPS | Слой, который нельзя наверстать, должен переживать потерю любой одной машины |
| 3 | Адаптивная нарезка запросов под лимит выдачи hh + загрузка деталей только по дельте ID | Иначе физически не собрать выдачу; инкрементальность возникает на ingestion, а не в dbt |
| 4 | Great Expectations удалён из стека | Дублирует dbt tests, нарушает собственное правило ADR из v1.0 §4.3 |
| 5 | ClickHouse перенесён в конец Фазы 2 / Фазу 3 | Не проектировать на двух движках одновременно; Postgres переваривает объём без усилий |
| 6 | Изменён порядок Фазы 2: снапшоты → SCD2 → правила → дедуп | От уникальной ценности к дорогим фишкам |
| 7 | Сроки ×2 при работе вечерами | Честная оценка вместо выгорания на просрочке |
| 8 | Добавлена задача ручной разметки 200–300 пар вакансий | Без неё precision дедупликации невозможно измерить |
| 9 | Зафиксирован источник курсов для UZS / KGS / RUB | Иначе `salary_usd` для этих стран будет NULL |

Дополнительно: `detect_closures` из отдельного DAG превращается в dbt-модель; SCD2 переводится на `dbt snapshot` — но после однократной ручной реализации (см. §12).

## 1. Цели

### 1.1 Учебная цель (основная для автора)

Сквозная дата-инженерия на реальной задаче: от сбора сырых данных до публичного продукта.

| Компетенция | Где отрабатывается |
|---|---|
| Ingestion из разнородных источников | Фаза 1–2 |
| Объектное хранилище как raw-слой | Фаза 1 |
| Операционка: алерты, ранбук, бэкфилл | Фаза 1 |
| Историзация данных (SCD Type 2) | Фаза 2 |
| Дедупликация и entity resolution | Фаза 2 |
| dbt: модели, тесты, документация, lineage | Фаза 2 |
| Оконные функции и аналитический SQL | Фаза 2 |
| Data Quality как отдельный слой | Фаза 2 |
| Оркестрация нетривиальных пайплайнов | Все фазы |
| LLM для structured extraction | Фаза 2 |
| Колоночная аналитическая СУБД (ClickHouse) | Фаза 3 |
| BI и публикация результатов | Фаза 3 |

### 1.2 Продуктовая цель

Дать соискателям и работодателям региона объективную картину рынка IT-труда: реальные зарплатные вилки, динамику спроса, время жизни вакансий, устаревающие и растущие технологии.

### 1.3 Ключевое отличие

Проект **не агрегатор вакансий**. Уникальная ценность — **накопленная история состояний рынка**, которой не хранит ни одна площадка. Из ежедневных снимков рождаются метрики, недоступные при взгляде на текущий срез.

**Главный операционный вывод:** накопление истории начинается с первого дня и не может быть наверстано позже. Приоритет Фазы 1 — запустить ежедневный сбор, даже если обработка ещё не готова.

## 2. Границы проекта

### 2.1 В скоупе

- Сбор IT-вакансий по Казахстану, Кыргызстану, Узбекистану; Россия — база для сравнения
- Ежедневная фиксация состояния каждой вакансии
- Нормализация профессий, грейдов, скиллов, зарплат
- Дедупликация между площадками
- Аналитические витрины и публичный дашборд
- Регистрация пользователей и подписки на фильтры (Фаза 4)

### 2.2 Вне скоупа

- Отклик на вакансию через платформу
- Скрейпинг площадок, запрещающих его в ToS
- Хранение резюме и ИИ-подбор — **вынесено в Фазу 5 как отдельный продукт** (см. §2.4)

### 2.3 Ограничения источников — принципиальные

| Желаемая метрика | Доступность | Решение |
|---|---|---|
| Количество откликов | Недоступна публично | Заменяется временем жизни вакансии |
| Динамика откликов | Недоступна | Заменяется фактом перепубликации |
| Факт закрытия вакансии | Недоступен явно | Выводится из исчезновения из выдачи |
| Реальная зарплата нанятого | Недоступна | Работаем только с заявленной вилкой |

**«Время закрытия вакансии» здесь и далее означает время присутствия в выдаче**, что не тождественно факту найма. Эта формулировка обязана присутствовать в публичной методологии.

> Если счётчик откликов обнаружится в публичной выдаче какого-либо источника — задача пересматривается отдельным ADR. Проверить на практике при подключении каждого источника.

### 2.4 Резюме и ИИ-подбор — отложено, не отменено

Задача «пользователь загружает резюме, ИИ подбирает вакансии и предлагает компании» вынесена в Фазу 5. Причины отсрочки:

- требует персональных данных с соответствующими правовыми обязательствами;
- бесполезна без качественных справочников профессий и скиллов, которые появляются только в конце Фазы 2;
- подписка на фильтр (Фаза 4) закрывает 80% той же потребности за 10% усилий.

Порядок обязателен: сначала подписки, потом умный подбор.

### 3.1 Приоритизация

| Приоритет | Источник | Метод | Оценка объёма | Фаза |
|---|---|---|---|---|
| P0 | hh (kz / uz / kg) | Официальный REST API | основной массив | 1 |
| P1 | hh.ru | Официальный REST API | база сравнения | 2 |
| P1 | Telegram-каналы | Telethon, публичные каналы | 50–200 постов/день | 2 |
| P2 | Хабр Карьера | HTML-парсинг | ~2–3 тыс. | 2 |

| P3 | LinkedIn | Не парсить | — | — |

LinkedIn исключён: антибот-защита и прямой запрет в ToS.

### 3.2 Особенности hh API — определяют форму ingestion

Три ограничения, вокруг которых строится клиент. **Проверить своими руками до реализации**, справочники и лимиты меняются.

**Лимит выдачи.** `page * per_page` ограничено сверху (по документации — 2000). Одним запросом «все IT-вакансии Казахстана» выдачу не получить.

Решение — **адаптивная нарезка**: запрос разбивается по `professional_role`, `area`, окнам `date_from` / `date_to`. Если `found` превышает лимит — окно делится дальше рекурсивно. Это первая настоящая инженерная задача проекта.

**Список не содержит описания.** Полный текст — только `GET /vacancies/{id}`, по одному запросу на вакансию.

Решение — **инкрементальность на уровне ingestion**: список забирается целиком ежедневно, детали грузятся только для новых или изменённых `id` (сравнение с вчерашним списком). Без этого — десятки тысяч лишних запросов в день.

**Один API на все страны.** `api.hh.ru` с параметрами `area` и `host`; hh.kz / hh.uz / hh.kg — не отдельные API. Один клиент, разные конфиги. Коды `area` брать из `GET /areas`, не хардкодить по памяти.

Зарегистрировать приложение и получить токен: анонимный доступ периодически ограничивают.

### 3.3 Требования к сбору

- **Порядок обязателен: `fetch → write_raw → validate → alert`.** Сырьё пишется всегда, до любой валидации.
- Pydantic на raw — с `extra="allow"`, задача модели на этом слое — **заметить изменение схемы и поднять алерт**, а не остановить запись. Строгие модели — только на staging.
- Rate limits с экспоненциальным backoff на `429` и `5xx`
- Осмысленный `User-Agent` с контактом
- Идемпотентность: повторный запуск за дату перезаписывает партицию целиком
- Полное сохранение сырого ответа без предварительной обработки
- Перед подключением каждого источника — проверка `robots.txt` и ToS, результат фиксируется в `docs/sources/<source>.md`. **Шаг обязателен и для Telegram, и для Хабра.**

## 4. Архитектура

### 4.1 Общая схема

```
┌─────────────────────────────────────────────────────────────┐
│  ИСТОЧНИКИ                                                  │
│  hh API  │  HTML-парсеры  │  Telegram (Telethon)            │
└────────────────────────┬────────────────────────────────────┘
                         │  Python: httpx
                         │  fetch → write_raw → validate → alert
                         ▼
┌─────────────────────────────────────────────────────────────┐
│  RAW  —  удалённый бакет (Cloudflare R2 / Backblaze B2)     │
│  Неизменяемые сырые ответы, живут отдельно от сервера       │
│  raw/{source}/country={cc}/dt={YYYY-MM-DD}/{kind}-{n}.json.gz│
└────────────────────────┬────────────────────────────────────┘
                         │  dbt
                         ▼
┌─────────────────────────────────────────────────────────────┐
│  STAGING  —  PostgreSQL 16                                  │
│  Типизация, нормализация, вырезание контактов               │
└────────────────────────┬────────────────────────────────────┘
                         │  dbt
                         ▼
┌─────────────────────────────────────────────────────────────┐
│  CORE  —  PostgreSQL 16 (+ pgvector)                        │
│  SCD2, снапшоты, справочники, дедупликация                  │
└────────────────────────┬────────────────────────────────────┘
                         │  dbt  →  Фаза 3
                         ▼
┌─────────────────────────────────────────────────────────────┐
│  MARTS  —  Postgres (Фаза 2)  →  ClickHouse (Фаза 3)        │
└────────────────────────┬────────────────────────────────────┘
                         ▼
              Metabase → DRF + React (Фаза 4)

        ┌────────────────────────────────────┐
        │  Airflow — оркестрация             │
        │  dbt tests — качество данных       │
        │  Telegram-бот — алерты             │
        └────────────────────────────────────┘
```

### 4.2 Обоснование технологий

| Технология | Роль | Обоснование |
|---|---|---|
| Python 3.12 + httpx | Ingestion | Retry/backoff, HTTP/2, простота |
| Pydantic | Детектор изменения схемы | На raw — сигнальный, на staging — строгий |
| R2 / B2 | Raw-слой | S3-совместимо, дёшево, переживает потерю VPS |
| PostgreSQL 16 + pgvector | Staging + Core + Marts (Фаза 2) | Транзакционность, оконные функции, векторы для дедупа в той же БД |
| dbt-core | Трансформации | Версионирование логики, тесты, lineage. Центральный обучающий элемент |
| Airflow 2.9, LocalExecutor | Оркестрация | TaskFlow API, dynamic task mapping. Celery не нужен |
| Metabase | BI | Один контейнер против четырёх у Superset |
| ClickHouse | Marts (Фаза 3) | Перенос готовых витрин с бенчмарком «до/после» |
| Docker Compose | Окружение | Воспроизводимость с первого дня |

### 4.3 Сознательно исключено

| Технология | Причина |
|---|---|
| Apache Spark | Объём на 2–3 порядка ниже порога окупаемости |
| Hadoop / HDFS | Вытеснен объектными хранилищами |
| Kafka | Нет источника реального времени до Фазы 5 |
| Debezium / CDC | Нет своей транзакционной базы до Фазы 4 |
| Great Expectations | Дублирует dbt tests. Разрастание стека |
| Superset | Тянет Postgres + Redis + Celery ради того же, что делает Metabase одним контейнером |
| Celery Executor | Один воркер, LocalExecutor достаточно |

**Правило:** новая технология входит в стек только через ADR в `docs/adr/` с ответом на вопрос «что сломается, если её убрать».

### 4.4 Ресурсы

VPS минимум 4 ГБ, рекомендуется 8. Airflow ~2–3 ГБ, Postgres ~1–2 ГБ, остальное — запас. Бакет — внешний, в бюджет VPS не входит.

Вести `docs/costs.md`: VPS, бакет, LLM-вызовы, домен. Помесячно.

## 5. Модель данных

### 5.1 Два ключа, а не один

Критическое различение. Их путаница ломает и дедупликацию, и статистику по компаниям.

**`(source, source_id)` — идентичность внутри источника.** Отвечает на «эта вакансия у нас уже была?». Есть у каждой площадки, стабилен, не конструируется. **Вводится в Фазе 1.**

**`vacancy_nk` — межплощадочная дедупликация.** Отвечает на «вакансия на hh и на Хабре — одна и та же?». Результат алгоритма из §6.1, а не конкатенация строк. **Фаза 2.**

Почему `{domain}-{company}-{title}` не работает как ключ:

- домен в ключе не даёт схлопнуть площадки — ради чего дедупликация и нужна;
- имя компании нестабильно («Kaspi.kz» / «ТОО Kaspi» / «Kaspi Bank» — три ключа на одну компанию);
- заголовок меняется при редактировании — вакансия «обнуляет» время жизни.

### 5.2 Слой CORE

**`dim_company`** — `company_sk` PK, `company_nk` (нормализованное имя), `name_original`, `inn_bin`, `is_agency`, `size_bucket`, `first_seen_at`, `last_seen_at`.

> Появляется **раньше** любой статистики по компаниям. Иначе «40 вакансий у компании» окажется четырьмя записями по 10 под разными написаниями.

**`dim_profession`** — `profession_sk`, `profession_code` (`backend_python`, `data_engineer`), `family` (`development`, `data`, `qa`, `devops`, `design`, `management`), `title_ru`/`title_en`, `is_deprecated`.

**`dim_skill`** — плоский справочник с группировкой (язык, фреймворк, СУБД, облако, инструмент).

**`fct_vacancy`** — SCD Type 2. Ключевые поля: `vacancy_sk`, `vacancy_nk`, `source`, `source_id`, `company_sk`, `profession_sk`, `title_original`, `grade`, `work_format`, `employment_type`, `city`/`country`, `salary_from`/`salary_to`/`salary_currency`/`salary_gross`, `salary_from_usd`/`salary_to_usd`, `published_at`, `valid_from`/`valid_to`/`is_current`, `is_active`, `closed_at`, `lifetime_days`.

**`fct_vacancy_snapshot`** — строка на вакансию на день. Основа времени жизни и обнаружения перепубликаций. **Самая ценная таблица проекта.**

**`bridge_vacancy_skill`** — многие-ко-многим с флагом `is_required`.

**`dim_currency_rate`** — курсы на дату.

### 5.3 Курсы валют — решено явно

| Валюта | Источник |
|---|---|
| KZT | Нацбанк РК |
| UZS | ЦБ Узбекистана |
| KGS | Нацбанк КР |
| RUB | ЦБ РФ |

Фолбэк — единый провайдер (exchangerate.host или аналог) при недоступности национального источника. Без этого решения `salary_usd` для Узбекистана и Кыргызстана останется NULL, и сравнение стран — главная фича продукта — не заработает.

### 5.4 Слой MARTS

| Витрина | Гранулярность | Назначение |
|---|---|---|
| `mart_salary_stats` | дата × профессия × грейд × город | Медиана, среднее, p25, p75, N |
| `mart_demand_trend` | неделя × профессия × страна | Динамика новых вакансий |
| `mart_skill_popularity` | месяц × скилл × профессия | Доля вакансий со скиллом |
| `mart_company_activity` | месяц × компания | Активность найма, перепубликации |
| `mart_vacancy_lifetime` | профессия × грейд | Распределение времени жизни |
| `mart_vacancy_flat` | вакансия | Денормализовано под поиск и фильтры |

**Правило публикации:** агрегированная зарплатная метрика не публикуется при менее чем **5 наблюдениях** в группе.

## 6. Ключевые алгоритмы

### 6.1 Дедупликация — по этапам, с замером между ними

**Этап 1 — точное совпадение.** `hash(normalize(title) + company_sk + city)`. Нормализация: нижний регистр, удаление пунктуации и эмодзи, синонимы («разработчик» → «developer»).

**Замер обязателен.** Сколько пар склеилось, сколько дублей осталось на глаз. **К этапу 2 не переходить, пока не доказано, что этап 1 не покрывает.**

**Этап 2 — нечёткое совпадение.** Эмбеддинги описаний, косинусное сходство, порог 0.92. Кандидаты — одна компания, окно ±14 дней. Векторы в pgvector.

**Этап 3 — ручное разрешение.** Пары 0.85–0.92 в очередь. Решения сохраняются и используются как обучающая выборка.

**Приоритет — precision над recall.** Ошибочно склеенные вакансии портят статистику необратимо; пропущенный дубль лишь слегка её размывает.

### 6.2 Разметка для замера качества — отдельная задача

Precision не считается сам. Нужно **вручную разметить 200–300 пар** вакансий: дубль / не дубль. Несколько вечеров работы.

Разметка делается **до** выбора порога 0.92 — иначе цифра остаётся цитатой из документа, а не собственным решением. Хранится в `enrichment/labels/` под git.

### 6.3 Детекция закрытий

dbt-модель (не отдельный DAG) поверх `fct_vacancy_snapshot` с оконной функцией.

**Защита от ложных закрытий:** вакансия помечается закрытой только после отсутствия в **двух последовательных** выгрузках. Один сбой парсера не должен «закрыть» весь рынок.

### 6.4 Распознавание профессий — правила прежде LLM

Порядок обязателен:

1. Регулярки + seeds-справочник. **Замерить долю нераспознанных.**
2. LLM — только для остатка, который правила не покрыли.
3. Замер на 200 размеченных примерах, подсчёт стоимости в день.

LLM без предварительного замера правилами — это оплата решения задачи, которая решается регуляркой.

## 7. Оркестрация

### 7.1 DAG `ingest_daily`

Ежедневно в 03:00 UTC+6.

```
start
  ├─ [dynamic task mapping по источникам]
  │    fetch_source(source)
  │      → write_raw_to_bucket      ← сырьё сохранено, что бы дальше ни случилось
  │      → validate_schema          ← сигнал, не шлагбаум
  │      → log_to_ingestion_log
  ├─ fetch_currency_rates
  └─ check_ingestion_completeness
       └─ trigger dbt_transform
```

Один DAG, источники разворачиваются через `.expand()`. Добавление площадки — модуль в `ingestion/sources/` плюс строка в реестре, не новый DAG.

Отказ одного источника не блокирует остальные. Отдельный DAG заводится только при принципиально другом расписании (Telegram в реальном времени, Фаза 5).

Порог алерта: падение источника или отклонение объёма более чем на 40% от скользящего среднего за 7 дней.

### 7.2 DAG `dbt_transform`

```
dbt run --select staging → dbt test --select staging
  → dbt run --select core → dbt test --select core
    → dbt run --select marts → dbt test --select marts
```

Провал тестов останавливает конвейер. Витрины сохраняют предыдущее валидное состояние.

### 7.3 Алертинг

Telegram-бот. Обязательные события: падение таски, **пропуск запуска DAG**, отклонение объёма, провал dbt-теста.

Без алерта на пропуск запуска дыру в данных обнаруживают через месяц, когда бэкфилл уже невозможен.

## 8. Качество данных и операционка

### 8.1 Проверки

| Слой | Проверка |
|---|---|
| Raw | Файл за дату существует, размер больше нуля |
| Raw | Количество записей в пределах ±40% от среднего за 7 дней |
| Staging | `source_id` уникален в пределах источника и даты |
| Staging | `published_at` не в будущем и не старше 2 лет |
| Staging | `salary_from` ≤ `salary_to` |
| Core | Ровно одна текущая версия на `vacancy_nk` |
| Core | Нет разрывов и пересечений интервалов `valid_from`/`valid_to` |
| Core | Все FK разрешаются |
| Marts | Медианная зарплата по профессии не меняется более чем на 30% за день |
| Marts | Доля нераспознанных профессий ниже 15% |

### 8.2 `meta.ingestion_log`

Обязательна: `run_id`, `source`, `started_at`, `finished_at`, `status`, `records_fetched`, `records_written`, `error_message`.

Без журнала через три месяца невозможно объяснить провалы в данных.

### 8.3 Ранбук и бэкфилл

`docs/runbook.md`: что делать при падении, как бэкфиллить, где логи, как проверить целостность за период. Писать так, будто читать будет посторонний — через полгода это вы.

`scripts/backfill.py --source hh_kz --dt 2026-09-12` — бэкфилл руками за 5 минут, не за вечер.

### 8.4 Учения по отказам

Раз в фазу — намеренная поломка с фиксацией результата в журнале:

- удалить день из бакета → проверить поведение детекции закрытий;
- подменить поле в ответе → поймал ли Pydantic, пришёл ли алерт;
- прогнать `ingest_daily` дважды за дату → идемпотентность;
- создать две `is_current = true` на один `vacancy_nk` → упал ли dbt-тест.

Поведение системы при сбое узнаётся только так.

## 9. Дорожная карта

> Сроки — для фултайма. **При работе вечерами умножать на два.**

### Фаза 1 — Накопление истории (2–3 недели)

Цель: сырьё копится в надёжном месте, о сбоях приходит алерт.

**День 1–2. Фундамент.** VPS, репозиторий, `.env` в `.gitignore`, `pyproject.toml`, `ruff`, `pre-commit`. Удалённый бакет. ADR-001 «Почему raw в удалённом объектном хранилище». `docs/journal.md` — первая запись.

**День 3–5. Клиент hh и запуск сбора cron'ом.** httpx с retry/backoff. Адаптивная нарезка под лимит выдачи. Список → дельта ID → детали только по новым. Идемпотентность. **Поставить в cron сразу.** Airflow подождёт неделю, история — нет.

**День 6–10. Airflow.** Docker Compose, LocalExecutor. `ingest_daily` с dynamic task mapping по `[hh_kz, hh_uz, hh_kg]`. `meta.ingestion_log`. Telegram-алерты. Cron выключается только после трёх суток стабильной работы Airflow.

**День 11–15. Операционка.** `backfill.py`. Проверка объёма ±40% как таска. Минимальная `stg_hh_vacancies` (jsonb + ключевые типизированные поля). `docs/runbook.md`. Первые учения по отказам.

**Критерий готовности:** 14 дней подряд без пропусков; бакет живёт отдельно от сервера; алерт сработал хотя бы раз и был отработан.

### Фаза 2 — Обработка (4–6 недель фултайм / 8–12 вечерами)

Порядок обязателен — от уникальной ценности к дорогому:

1. `fct_vacancy_snapshot` + `lifetime_days` + детекция закрытий (правило двух выгрузок). Дёшево по коду, уникально по ценности. Через месяц — метрика, которой нет ни у кого.
2. SCD2 по вакансиям. **Сначала руками**, потом `dbt snapshot` (см. §12).
3. Справочник профессий по правилам. Замерить долю нераспознанных.
4. Нормализация зарплат и курсы валют. Первые честные dbt tests.
5. `dim_company` с нормализацией имён.
6. Разметка 200–300 пар для дедупа.
7. Дедуп, этап 1. Замерить, сколько склеилось.
8. Telegram и Хабр — только когда core стабилен на hh. С правовой проверкой в `docs/sources/`.
9. LLM-извлечение — только для непокрытого правилами. Замер на 200 примерах, подсчёт стоимости.
10. Дедуп, этап 2 (pgvector) — только если этап 1 показал потребность.
11. Витрины в Postgres.

Каждый пункт — отдельная ветка, отдельный PR самому себе, отдельная запись в журнале **с числами**.

**Критерий:** витрины считаются, тесты зелёные, доля нераспознанных профессий ниже 15%, precision дедупа измерен.

### Фаза 3 — Публикация (2–3 недели)

- ClickHouse: перенос **готовых** витрин. ADR + бенчмарк «до/после». Здесь изучаются движки таблиц, `ReplacingMergeTree`, материализованные вьюхи — на реальной задаче миграции.
- Metabase, набор дашбордов
- Публичный доступ, домен, SEO
- `docs/methodology.md` — публичная методология: как считается, чего не показывает, что «закрытие» ≠ найм

**Критерий:** посторонний человек открывает дашборд и получает ответ на «сколько платят Python-разработчику middle в Алматы».

### Фаза 4 — Пользователи (3–4 недели)

DRF + React. Причина не в моде: две разные нагрузки — агрегаты из витрин и транзакционные данные пользователей. Шаблоны Django упрутся на графиках истории.

- Регистрация, сохранённые фильтры
- Email-подписка на новые вакансии по фильтру
- История вакансии и история компании как публичные страницы
- «Мой рынок» — динамика по интересующим направлениям

Фронтенд пишется **после** Metabase: половина задуманных экранов отпадёт, не будучи написанной.

### Фаза 5 — Развитие

- **Резюме и ИИ-подбор** (см. §2.4): загрузка резюме, извлечение скиллов, матчинг к вакансиям, рекомендации компаниям. Требует отдельного ADR по обработке персональных данных.
- Ежеквартальные аналитические отчёты
- Публичное API
- Прогнозирование спроса
- Мониторинг Telegram в реальном времени — здесь Kafka становится оправданной

## 10. Правовые и этические требования

- Собираются только публично опубликованные данные вакансий
- Персональные данные соискателей не собираются (до Фазы 5, где режим меняется отдельным ADR)
- Контакты из текстов вакансий вырезаются на staging
- Соблюдаются rate limits и `robots.txt`; результат проверки — в `docs/sources/<source>.md` **до подключения источника**
- Публикуются агрегаты; полные чужие тексты не воспроизводятся, даётся ссылка на первоисточник
- На дашборде — источник данных и дата последнего обновления
- Методология публикуется открыто, включая оговорку про «закрытие» ≠ найм

## 11. Риски

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Потеря истории из-за простоя | Средняя | **Критическое** | Алерт на пропуск запуска, бэкфилл за 24 часа, бакет вне VPS |
| Потеря дня из-за падения валидации | **Была высокой в v1.0** | **Критическое** | Снята правкой порядка: `write_raw` до `validate` |
| Изменение схемы API | Высокая | Среднее | Pydantic с `extra="allow"` на raw, алерт |
| Лимиты выдачи / блокировка | Высокая | Высокое | Адаптивная нарезка, backoff, токен приложения |
| Низкое качество дедупа | Высокая | Высокое | Разметка, precision над recall, очередь разрешения |
| Малый объём данных по KZ | Средняя | Среднее | Порог 5 наблюдений, укрупнение группировок |
| Разрастание стека | **Высокая** | **Высокое** | ADR на каждый инструмент, тест «убери и объясни» |
| Выгорание на просрочке | Средняя | Высокое | Сроки ×2 для вечерней работы, узкие итерации |

Главный риск не технический. Пет-проекты чаще умирают от переусложнения стека, чем от скучных инструментов.

## 12. Правила работы — против вайбкодинга

Критерий владения кодом: **можете ли вы удалить файл и написать его заново без подсказки?** Если нет — код не ваш, независимо от того, работает ли он.

### 12.1 Что пишется руками

| Своими руками | Можно делегировать |
|---|---|
| DAG'и, dynamic task mapping | docker-compose, Dockerfile |
| Клиент hh, адаптивная нарезка | boilerplate DRF, сериализаторы |
| SCD2 — первая реализация | React-компоненты, вёрстка |
| Дедупликация целиком | миграции |
| Оконные функции, `lifetime_days` | конфиги Metabase |
| dbt-модели core | — |

Левая колонка — таблица компетенций из §1.1. Остальное — обвязка, на ней ничему не научишься.

**Отдельно про SCD2 и детекцию закрытий.** В продакшене — `dbt snapshot` и оконная функция. Но оба пункта в списке целевых компетенций, поэтому: реализовать руками на малом наборе, сломать (две текущие версии, разрыв интервалов), затем заменить на `dbt snapshot` и сравнить. Готовый snapshot без понимания — тот же вайбкодинг, только через dbt.

### 12.2 Практики

- **ADR до кода.** Ни строки с новой технологией, пока не написан ADR с альтернативой и причиной отказа.
- **Сначала руками, потом автоматизация.** Дёрнуть API в REPL, посмотреть JSON, написать SQL в psql — и только потом заворачивать в DAG.
- **Ломать специально** (§8.4).
- **Журнал.** Еженедельно 10 строк: что сделал, что сломалось, что бы сделал иначе. С числами.
- **Тест «убери и объясни».** Для каждого компонента: что будет, если убрать? «Ничего страшного» — убирать.
- **Explain-back.** Объяснить вслух после каждого крупного куска. Где запнулся — то и не понял.
- **Ревью себя с задержкой.** Открыть свой код через две недели, найти непонятное, записать.
- **Проверять источники, включая ИИ.** Коды `area`, лимиты, синтаксис dbt — сверять с документацией. Ассистент ошибается.

### 12.3 Как спрашивать ассистента

| Плохо | Хорошо |
|---|---|
| «напиши DAG для hh» | «вот мой DAG, что сломается при 429?» |
| «сделай дедупликацию» | «я выбрал порог 0.92, аргументы за и против?» |
| «как правильно» | «вот моя схема SCD2, найди дыры» |

Требовать объяснения «почему», а не готового кода. Если решение непонятно — останавливать и разбирать.

## 14. Первый шаг

Не проектирование, не выбор инструментов, не чтение документации.

1. Создать бакет в R2 или B2
2. Написать ~80 строк на httpx: запрос к `api.hh.ru/vacancies`, пагинация, gzip, запись в бакет
3. Поставить в cron на 03:00
4. Завести `docs/journal.md`, первая строка: дата и «сбор запущен»

Всё остальное строится над данными, которые уже лежат. Данные, не собранные сегодня, не собираются никогда.
